# Структура учебного проекта PostgreSQL и Citus

Проект представляет собой стенд для изучения динамического шардирования PostgreSQL с расширением Citus. Веб-приложение на Python и Flask позволяет просматривать тестовые данные, проверять состояние кластера и запускать подготовленные операции управления. SQL-скрипты задают схему данных, распределение таблиц, проверки и нагрузочные сценарии.

Структура составлена по требованиям `ТЗ.docx`, описанию в `Text.docx` и дополнению о простом веб-интерфейсе. Названия файлов и разделение кода ниже являются проектным решением. Этот документ описывает будущие файлы; их наличие в дереве не означает, что они уже созданы.

## 1. Состав системы

В начальной конфигурации работают координатор Citus и два рабочих узла. Для эксперимента с масштабированием предусмотрен третий рабочий узел. Отдельный экземпляр PostgreSQL без Citus используется для сравнения производительности.

```text
Браузер
  │
  ▼
Веб-приложение Flask
  │
  ▼
Координатор Citus
  ├── worker-1
  ├── worker-2
  └── worker-3 — подключается в эксперименте

Нагрузочные сценарии
  ├── координатор Citus
  └── PostgreSQL без Citus

Экспортёры метрик узлов → Prometheus → Grafana
```

Flask обращается к координатору. Маршрутизацию запросов, распределённое выполнение и перенос шардов осуществляет Citus. Приложение предоставляет интерфейс к этим операциям, но не реализует собственный алгоритм шардирования.

Для учебного варианта достаточно Flask, HTML-шаблонов и CSS. Отдельный JavaScript-фреймворк, ORM, REST API и очередь задач на первом этапе не нужны. Веб-приложение предполагается использовать локально, без регистрации пользователей и разграничения ролей.

## 3. Файлы в корне проекта

### `README.md`

Инструкция по использованию готового проекта. Содержит требования к окружению, закреплённые версии PostgreSQL и Citus, порядок запуска контейнеров и Flask, настройку подключений и последовательность выполнения SQL-скриптов. Здесь же описываются запуск экспериментов, просмотр результатов и остановка стенда.

Этот файл должен позволять повторить эксперимент на другом компьютере. Он описывает фактическую реализацию, тогда как настоящий документ задаёт план структуры.

### `.gitignore`

Исключает из Git файл `.env`, виртуальное окружение Python, кэш Python, временные журналы и локальные данные БД. Итоговые результаты экспериментов можно сохранять в репозитории, если они нужны для отчёта и не занимают большой объём.

### `.env.example`

Образец настроек без настоящих паролей. Содержит имена переменных для адреса координатора, порта, имени базы, пользователя, пароля, подключения к монолиту и параметров Flask. Для каждой настройки следует указать понятное примерное значение или пояснение.

### `.env`

Локальная конфигурация конкретного запуска. Создаётся пользователем на основе `.env.example`. Python и Compose используют согласованные имена переменных. Файл не включается в Git.

Адреса зависят от места запуска: Flask на Windows подключается через опубликованный порт, а контейнеры внутри одной сети Docker используют имена сервисов. Эти варианты нужно явно описать в README.

### `requirements.txt`

Список зависимостей Python: Flask, `psycopg` с выбранным способом установки и `python-dotenv`. После проверки приложения здесь закрепляются конкретные версии для воспроизводимого запуска. Этот файл не устанавливает PostgreSQL, Citus или Docker.

### `compose.yaml`

Описание контейнеров координатора, рабочих узлов, монолитной БД, экспортёров метрик, Prometheus и Grafana. Задаёт образы с фиксированными версиями, сеть, порты, тома, переменные окружения и проверки готовности сервисов.

Третий рабочий узел следует запускать отдельно по требованию, например через профиль Compose. Мониторинг также можно выделить в отдельный профиль, чтобы сначала отладить БД. Монолит и кластер допускается тестировать по очереди, если ресурсы компьютера ограничены.

В первой версии Flask запускается в виртуальном окружении на компьютере разработчика. Отдельный Dockerfile для него пока не требуется. Инициализацию схемы лучше выполнять явными шагами из README, чтобы было видно, когда создаются таблицы и когда происходит их распределение.

## 4. Папка `infrastructure/`

Содержит настройки виртуальной машины. Она нужна при использовании схемы Windows → VirtualBox и Vagrant → Ubuntu → Docker. На уже подготовленном Ubuntu-сервере этот этап можно пропустить.

### `Vagrantfile`

Определяет образ Ubuntu, число процессоров, объём памяти, сеть, проброс портов и общую папку с проектом. Подключает сценарий подготовки `provision.sh`. Ресурсы должны соответствовать фактическому эксперименту и быть отражены в отчёте.

### `provision.sh`

Подготавливает Ubuntu: устанавливает Docker, Compose и необходимые клиентские инструменты PostgreSQL, включая `psql` и `pgbench`. Проверяет доступность установленных средств. Не должен автоматически удалять существующие базы или запускать нагрузочные эксперименты.

## 5. Папка `web/`

Содержит веб-приложение. Ответственность разделена между обработкой HTTP-запросов, соединением с БД и прикладными операциями.

### `app.py`

Создаёт приложение Flask, загружает настройки и объявляет маршруты. Получает значения форм, проверяет обязательные поля, вызывает функции из `services.py` и передаёт результат шаблону.

Предлагаемые страницы:

| Адрес | Назначение |
|---|---|
| `/` | Сводка состояния БД и количества записей |
| `/data` | Просмотр пользователей и заказов, поиск по пользователю |
| `/cluster` | Узлы, шарды и состояние операций управления |
| `/checks` | Проверки целостности и фиксированные диагностические запросы |

Действия, изменяющие данные или состав кластера, выполняются отдельными POST-запросами. Обычное открытие страницы ничего не изменяет. После отправки формы приложение возвращает пользователя на страницу с сообщением о результате, чтобы обновление страницы не повторяло операцию.

### `db.py`

Читает параметры подключения и предоставляет функции выполнения запросов. Управляет соединениями, фиксацией транзакций, откатом при ошибке и освобождением ресурсов. При необходимости поддерживает отдельные подключения к координатору и монолиту.

Значения из форм передаются параметрами драйвера. Не следует собирать SQL конкатенацией пользовательского ввода. Для операций Citus нужно отдельно учитывать требования конкретной функции к транзакциям; универсальная обёртка не должна принудительно помещать все административные команды в одну транзакцию.

### `services.py`

Содержит операции приложения: получение сводки, просмотр пользователей, поиск заказов, создание заказа, чтение состояния узлов и шардов, запуск балансировки и проверки целостности. Использует `db.py` и подготовленные SQL-запросы.

Здесь проверяются условия выполнения действий: например, нельзя повторно подключать зарегистрированный узел или удалять узел до переноса данных. В первой версии кнопка добавления узла работает с заранее настроенным `worker-3`. Приложение не создаёт контейнеры.

Путь к папке `sql/` вычисляется относительно расположения исходного кода, а не текущего каталога запуска. Запросы для `psycopg` и `pgbench` могут иметь разный синтаксис параметров. Если один файл нельзя использовать напрямую в обоих случаях, тонкая адаптация выполняется явно; механическая подстановка пользовательских строк не допускается.

### Папка `templates/`

Хранит HTML-шаблоны Jinja, которые Flask заполняет данными перед отправкой в браузер.

| Файл | Ответственность |
|---|---|
| `base.html` | Общая разметка, меню, подключение CSS, сообщения об успехе и ошибках, область содержимого страницы |
| `index.html` | Доступность БД, число рабочих узлов и сводные количества пользователей, заказов и событий |
| `data.html` | Таблицы пользователей и заказов, фильтр по `user_id`, форма создания заказа, ограничение выдачи или постраничный просмотр |
| `cluster.html` | Таблица узлов, размещение и размеры шардов, кнопки добавления узла, балансировки и обновления состояния |
| `checks.html` | Запуск фиксированных проверок, отображение результатов и времени выполнения коротких запросов |

В шаблонах нет SQL и логики подключения. Они получают готовые данные. При отсутствии записей или недоступности БД показывают понятное сообщение, а не пустую таблицу без объяснения.

### Папка `static/` и файл `style.css`

Папка содержит статические ресурсы, которые браузер получает без обработки шаблонизатором. В начальной версии достаточно `style.css`: оформление меню, таблиц, форм, кнопок и сообщений. Отдельный JavaScript-файл не требуется, поскольку страницы обновляются обычными запросами.

## 6. Папка `sql/`

Хранит SQL по назначению. Скрипты создания и административные операции выполняются осознанно, отдельно от обычного просмотра страниц. Часть запросов используется веб-приложением, часть предназначена для подготовки и экспериментов.

### Папка `setup/`

Содержит подготовку схемы и кластера. Нумерация задаёт общий порядок, но не означает выполнение каждого файла на каждом сервере.

| Файл | Назначение и место выполнения |
|---|---|
| `01_enable_extensions.sql` | Подключает Citus в нужных базах координатора и рабочих узлов. В монолитной БД Citus не подключается |
| `02_register_workers.sql` | Регистрирует начальные `worker-1` и `worker-2` у координатора после проверки готовности узлов |
| `03_create_schema.sql` | Создаёт таблицы, индексы и ограничения. Общая логическая схема используется в монолите и на координаторе |
| `04_seed_reference_data.sql` | Заполняет справочники статусов заказов и типов событий одинаковыми значениями |
| `05_distribute_tables.sql` | На координаторе создаёт распределённые таблицы по `user_id`, задаёт совместное размещение связанных таблиц и переводит справочники в эталонные |

Для демонстрации миграции можно после создания схемы и справочников загрузить небольшой набор данных, а затем выполнить распределение. Для основного нагрузочного эксперимента допустимо сначала распределить пустые таблицы, затем загрузить полный набор. Выбранный порядок фиксируется в README.

Предлагаемая схема:

| Таблица | Основные поля | Ключ и размещение |
|---|---|---|
| `users` | `user_id`, `name`, `email`, `created_at` | Первичный ключ `user_id`, распределение по `user_id` |
| `orders` | `user_id`, `order_id`, `status_id`, `total_amount`, `created_at` | Первичный ключ `(user_id, order_id)`, распределение по `user_id` |
| `events` | `user_id`, `event_id`, `event_type_id`, `created_at`, `payload` | Первичный ключ `(user_id, event_id)`, распределение по `user_id` |
| `order_statuses` | `status_id`, `name` | Эталонная таблица в Citus, обычная таблица в монолите |
| `event_types` | `event_type_id`, `name` | Эталонная таблица в Citus, обычная таблица в монолите |

Порядок создания ограничений и преобразования таблиц следует проверить на выбранной версии Citus. Механизм генерации идентификаторов должен быть единым для загрузчика и веб-приложения, чтобы ручное добавление заказа не пересекалось с тестовыми идентификаторами.

### Папка `data/`

Содержит `generate_data.sql`, который создаёт тестовых пользователей, заказы и события. Объёмы задаются параметрами. Генерация должна быть воспроизводимой: одинаковые параметры дают одинаковый исходный набор в монолите и кластере. Для случайных значений используется фиксированное начальное состояние генератора либо детерминированные формулы.

Повторный запуск должен иметь явно описанное поведение. Нельзя незаметно удваивать объём данных или удалять существующие записи. Очистка тестовой базы выполняется отдельным осознанным шагом, если она нужна.

### Папка `queries/`

Содержит запросы к предметным данным.

| Файл | Что выполняет |
|---|---|
| `insert_order.sql` | Добавляет заказ существующему пользователю с допустимым статусом и суммой |
| `select_user_orders.sql` | Возвращает заказы конкретного пользователя по `user_id` с ограничением выдачи |
| `join_user_orders.sql` | Соединяет пользователей и заказы по `user_id`, позволяя проверить работу связанных распределённых таблиц |
| `aggregate_orders.sql` | Рассчитывает число заказов и суммы по выбранным группам; общий запрос без фильтра пользователя используется для исследования нескольких шардов |

Запросы для веб-просмотра ограничивают размер ответа. Ограничения, сортировка и параметры нагрузочных вариантов фиксируются отдельно, чтобы сравнивать одинаковые операции.

### Папка `cluster/`

Содержит управление составом кластера. Эти операции выполняются на координаторе.

| Файл | Что выполняет |
|---|---|
| `add_worker.sql` | Регистрирует заранее запущенный третий рабочий узел |
| `rebalance.sql` | Запускает перераспределение шардов после изменения состава кластера |
| `drain_worker.sql` | Переносит шарды с выбранного узла на остальные узлы |
| `remove_worker.sql` | Удаляет освобождённый узел из метаданных кластера после проверки отсутствия размещённых на нём данных |

Регистрация узла сама по себе не означает завершение балансировки. Запуск переноса также не означает его успешное завершение: состояние нужно проверять отдельно.

Для веб-интерфейса необходимо выбрать поддерживаемый закреплённой версией Citus способ фонового запуска балансировки. Страница возвращает управление пользователю и затем показывает состояние по кнопке «Обновить». Фоновые потоки внутри Flask не используются как замена управлению длительными заданиями. Если конкретную операцию нельзя надёжно запустить в фоне средствами БД, она остаётся административным SQL-сценарием до отдельной реализации.

Удаление узла из Citus и остановка его контейнера — разные действия. Сначала завершаются перенос данных и удаление из метаданных, затем контейнер можно остановить средствами Docker.

### Папка `monitoring/` внутри `sql/`

Хранит диагностические запросы к PostgreSQL и Citus.

| Файл | Что показывает |
|---|---|
| `nodes_and_shards.sql` | Зарегистрированные рабочие узлы, размещение, количество и размеры шардов, доступные сведения о ходе перераспределения |
| `activity_and_locks.sql` | Активные запросы, длительные операции, ожидания и блокировки |

Названия системных представлений и доступные столбцы проверяются для установленной версии. Список зарегистрированных узлов не следует выдавать за проверку их текущей сетевой доступности. Доступность определяется отдельной проверкой.

### Папка `checks/`

Содержит `check_integrity.sql`: количество записей, контрольные суммы денежных итогов, поиск заказов без пользователей и других нарушений связей. Проверки выполняются до и после распределения и переноса шардов, а также при сравнении монолита с кластером.

Совпадение числа строк и сумм полезно, но не доказывает полное совпадение всех данных. Для выбранного тестового набора следует дополнительно сравнивать результаты контрольных запросов с одинаковой сортировкой. Если во время балансировки идут вставки, итог сравнивается с учётом успешно завершённых операций; простое равенство показателей «до» и «после» в таком случае не ожидается.

## 7. Папка `benchmarks/`

Содержит средства воспроизводимого сравнения производительности. Веб-проверки используются для демонстрации и диагностики, а нагрузочные измерения выполняются отдельно.

### `run_benchmarks.sh`

Запускает сценарии через `pgbench` для выбранной БД. Принимает параметры подключения, число клиентов, длительность, число повторов и название конфигурации. Сохраняет параметры запуска, задержки, пропускную способность, число ошибок и журналы в соответствующий каталог `results/`.

Перед измерением предусматривает одинаковую подготовку статистики и прогрев, если прогрев включён в методику. Тесты вставки меняют данные, поэтому для повторов нужен явно описанный способ восстановления исходного набора или учёта накопленных записей. Скрипт запускается в Ubuntu или другой подготовленной Linux-среде.

### `explain_queries.sql`

Содержит команды анализа планов для выборки по пользователю, соединения и агрегации. Результаты помогают объяснить обращение к одному или нескольким шардам, сетевые операции и различия с монолитом.

При использовании `EXPLAIN ANALYZE` запрос действительно выполняется. Поэтому анализ изменяющих запросов требует отдельного тестового сценария; в начальном варианте этот файл можно ограничить чтением данных.

## 8. Папка `monitoring/` в корне

Содержит конфигурацию внешнего мониторинга. В отличие от `sql/monitoring/`, здесь описывается подключение сервисов и отображение метрик, а не ручная SQL-диагностика.

### `prometheus.yml`

Задаёт адреса экспортёров, интервалы сбора и метки узлов. Prometheus получает метрики от экспортёров, а не подключается к PostgreSQL как SQL-клиент. Для координатора, рабочих узлов и монолита должны быть различимые метки.

### `exporter_queries.yaml`

Описывает дополнительные SQL-метрики, если выбранный экспортёр поддерживает такой формат. Его версию и поддержку пользовательских запросов нужно закрепить при реализации. Запросы Citus выполняются только там, где доступны нужные расширения и представления; монолит не должен получать запросы к отсутствующим объектам Citus.

В базовом варианте собираются показатели БД, соединений и распределения данных. Для CPU, памяти и диска хоста потребуется отдельный системный экспортёр, а для ресурсов контейнеров — соответствующий источник метрик. Один PostgreSQL-экспортёр не покрывает все показатели ресурсов.

### Папка `grafana/`

Хранит настройки автоматического подключения источника данных и панели мониторинга.

| Файл | Назначение |
|---|---|
| `datasource.yml` | Подключает Prometheus как источник данных Grafana |
| `dashboards.yml` | Указывает Grafana, где загружать сохранённые панели |
| `cluster_dashboard.json` | Описывает панели состояния узлов, соединений, размеров шардов и других фактически собираемых метрик |

JSON панели можно получить экспортом из Grafana после её настройки. Отображать следует только показатели, для которых настроен сбор: отсутствие источника нельзя подменять нулём на графике.

## 9. Папка `results/`

Содержит результаты запусков, а не исходный код. Подкаталоги разделяют конфигурации экспериментов.

| Папка | Содержимое |
|---|---|
| `baseline/` | Измерения PostgreSQL без Citus |
| `citus_2_workers/` | Измерения кластера с двумя рабочими узлами |
| `citus_3_workers/` | Измерения с тремя рабочими узлами после завершения балансировки |
| `rebalance/` | Длительность и ход переноса, размещение шардов до и после, ошибки и показатели нагрузки во время переноса |

Внутри каждой папки для отдельного запуска создаётся каталог с датой и идентификатором опыта. Пример состава такого каталога:

| Файл результата | Что сохраняется |
|---|---|
| `parameters.json` | Версии ПО, ресурсы, объём данных, число клиентов, длительность и параметры сценария |
| `summary.csv` | Сводные показатели выполнения |
| `pgbench.log` | Исходный вывод нагрузочного инструмента |
| `plans.txt` | Планы выбранных запросов |
| `integrity.txt` | Результаты проверок данных |
| `shards_before.csv` | Размещение шардов перед переносом, если перенос входит в опыт |
| `shards_after.csv` | Размещение шардов после переноса |

Эти файлы создаются по необходимости. Пароли и строки подключения с паролями в результаты не записываются. Предыдущие измерения не перезаписываются новым запуском.

## 10. Порядок разработки

1. Закрепить совместимые версии PostgreSQL и Citus, подготовить окружение и параметры ресурсов.
2. Создать `compose.yaml`, `.env.example`, `.env` и `.gitignore`; при использовании VM подготовить `infrastructure/`.
3. Запустить координатор, два рабочих узла и монолит, проверить соединения.
4. Написать и проверить скрипты `sql/setup/`, генерацию данных и обычные запросы.
5. Проверить целостность после распределения данных.
6. Создать `requirements.txt`, затем `db.py`, минимальный `app.py` и главную страницу.
7. Добавить `services.py`, просмотр данных и создание заказа.
8. Реализовать административные SQL-сценарии, затем подключить проверенные действия к странице кластера.
9. Подготовить нагрузочные тесты, сравнить монолит и кластер, проверить масштабирование под нагрузкой.
10. Подключить Prometheus и Grafana, сохранить конфигурацию панели.
11. Дополнить README фактическими командами запуска и оформить результаты для курсовой.

## 11. Условия готовности

Проект готов к демонстрации, когда стенд запускается по README, веб-интерфейс показывает реальные данные, новый заказ сохраняется и находится по пользователю, а распределённые таблицы размещены на рабочих узлах.

Эксперимент с расширением должен показать регистрацию третьего узла, завершённый перенос части шардов и корректность данных после переноса. Эксперимент с уменьшением кластера должен включать освобождение узла от данных до его удаления.

Для сравнения производительности нужны одинаковые исходные данные и запросы, зафиксированные ресурсы и повторные измерения. Работа всех контейнеров на одном компьютере исследует поведение Citus в пределах ресурсов этого компьютера; её результаты не следует представлять как измерение масштабирования на независимых физических серверах.
